6 つの調査エージェントで並列に集めた事実(出典付き)と、そこから導いた設計。実装は docs/自動歩行_障害物停止_横移動.md §6b-15。

## 設計の結論(要約)

Simplest robust design for THIS firmware: stay in the legacy walk FSM 200 (which the firmware reads back as the 29-DoF 'regular control' 501; never use Start()=500, it is silently ignored — matches unitree_sdk2_python issue #170), put the controller in balance mode 0 ('Standing Mode', = what the handheld remote uses) ONCE while stationary right after entry, stream SetVelocity(vx,0,0,duration=0.3..0.5) at 10 Hz with a LiDAR-range-based decel profile that never dips into the 0<cmd<0.30 stepping-in-place band, then switch to zero and let the controller settle itself; declare 'stopped' from the firmware signal GetFsmMode/rt/sportmodestate.fsm_mode==0 (not a timer), and only then optionally park in 802 (existing, measured-working 200->802 path) or leave it standing in 200/mode-0. Do not use SetFsmId(4) from walking (refused while fsm_mode==1 by documented design), do not use Damp() as a stop (it is the e-stop), and do not use ContinuousGait/balance mode 1 (documented to keep stepping at zero). The 20-50 cm backward drift is most plausibly an untrimmed backward bias of the walk controller (your own fit gives about -0.04 m/s at cmd 0) plus stepping-in-place with balance mode 1 / momentum from a hard cut — first check GetBalanceMode (7003) reads 0, reset the remote's stored Offset Compensation, ramp instead of cutting, and fold the residual into the LiDAR stop margin. Hold on speed mapping: use the fixed measured map v = 0.4*(cmd-0.10) with no adaptive learning (calib_learn stays False), since learning made the commands smaller and increased the backward drift.

### API の順序
- 0. Preconditions: robot standing (FSM 4 or 802) with the remote's walk mode NOT in 'Keep stepping' (double-click START toggle) and no stored offset; fsm_mode readable from rt/sportmodestate (fw>=1.5.1; fw_profile.py already subscribes). client.SetTimeout(10.0); enableLease=False as today.
- 1. GetFsmId() [7001]. If already in WALK_FSMS {200,500,501} skip to step 3.
- 2. Enter walking: if in 801/802 try SetFsmId(200) directly (measured OK on 9/3: 200/501/4 <-> 802 in ~0.4 s); if refused, SetFsmId(4)... wait until GetFsmMode()==0 ... SetFsmId(200). Poll GetFsmId() every 0.2 s up to ~4 s until it reads 200 or 501 (SetFsmId returns 0 even when refused; success 'depends on the built-in operation control state switching logic'). Keep 500 as a last fallback only (it wastes 6 s on this FW). Optionally try SetFsmId(501) explicitly before 200 and log which one sticks — UNVERIFIED on this unit, it is the community-verified walk state on sw 1.5.3 (xr_teleoperate PR #312/#322).
- 3. Wait until the robot is static in the walk FSM: poll _Call(7002,'{}') -> fsm_mode == 0 for 5 consecutive samples at 10 Hz (or rt/sportmodestate.fsm_mode). While waiting, do NOT send velocity.
- 4. Set standing (non-continuous) gait ONCE while static: SetBalanceMode(0) [7102]; read back _Call(7003,'{}') and require 0. If it reads 1, the remote left 'Keep stepping' on — this alone explains stepping forever at zero. Never send SetBalanceMode mid-walk (the earlier backward-walk incident). Do NOT send SetSpeedMode(7107) here: it is documented only for run mode (801/802) with values 0..3 (=1.0/2.0/2.7/3.0 m/s); -1 is undocumented; effect in 200/501 unknown. Remove it from the walking entry path or gate it behind an explicit operator flag.
- 5. Walk: 10 Hz loop, each tick compute d = LiDAR range to wall (toe-referenced, front_offset applied) and e = d - stop_dist; choose cmd from the profile in distance_control; SetVelocity(cmd, 0, omega_track, duration=0.4). Every tick re-sends (latest command replaces the previous one and restarts its hold; no documented planner reset, so re-sending identical values at 10 Hz is the intended pattern). Watchdog: if LiDAR is stale > 0.3 s or the loop misses a tick, send SetVelocity(0,0,0,0.4) — the 0.4 s hold means a dead process auto-stops within 0.4 s.
- 6. Stop: when e <= stop_margin (see distance_control) switch the streamed command to SetVelocity(0,0,0,0.4) and keep streaming zeros at 10 Hz for at least 2 s and until fsm_mode==0 for 5 consecutive samples (1.0 s at 10 Hz). Balance mode 0 is the documented mechanism that makes the legs stop: 'when the speed command is 0 and the robot is stable, the robot stops stepping'.
- 7. Verify with LiDAR after fsm_mode==0: if the robot ended more than tol (e.g. 8 cm) short (backward drift), issue ONE correction burst at cmd_min_walk (0.30) for the computed time using the fixed map, then zeros again and repeat the settle wait (max 2 corrections). Use LiDAR only; odometry counts stepping-in-place.
- 8. Park (optional, only after fsm_mode==0): SetFsmId(802) (measured to work from 200 in 0.4 s and to ignore 7105, so it is a safe 'velocity-deaf' standing state on this FW). Do NOT attempt SetFsmId(4) from 200 (refused while dynamic; the documented path to 4 is via damp, 1 -> 4) and do NOT use Damp() (robot goes limp). Leaving it in 200 with balance mode 0 is equally acceptable — it stands still by documentation — and is simpler; pick 802 only if the operator wants a state that cannot be moved by a stray velocity command.
- 9. Before any later posture/UserCtrl handover keep the existing 802 -> SwitchToUserCtrl(7110) -> 1000 path (undocumented but measured; the official example enters from FSM 1).

### 速度指令の送り方

Use SetVelocity(vx, vy, omega, duration) at 10 Hz with duration 0.3-0.5 s (recommend 0.4 s = 4 send periods) instead of the current cmd_dur=2.0 (autowalk.py line 80/642). Documented semantics (support.unitree.com sport_services_interface, Move/SwitchMoveMode/SetVelocity rows): the controller applies the LATEST command immediately, holds it for `duration`, and 'automatically stops' when the hold expires with no newer command; re-sending replaces/restarts the hold. Nothing indicates a re-send resets a planner or causes a hitch — the remote and Unitree's own examples rely on exactly this. Do not use Move(continuous=True): it is just duration 864000 s, so a crashed sender leaves the robot walking. Do not use StopMove()/duration 1.0 for the stop — use explicit zeros streamed at the same 10 Hz so 'zero' is unambiguously the latest command and the dead-man stays short. 2.0 s was not itself causing the extra stepping (a zero overwrites it), but it added up to 2 s of ambiguity after a stalled stream. Always send vy=0; steer only with small omega from wall tracking (om_turn 0.30 cap). Python _Call is blocking (waits for the RPC reply): time the loop on the wall clock and skip, not queue, late ticks.

### 止め方

Do not 'cut and hope' and do not stop with an FSM change. Sequence: (a) decelerate on the LiDAR range (profile below) so the last ~0.6 m are walked at the creep command 0.30 (actual ~0.08 m/s); (b) at stop_margin switch to streamed zeros (SetVelocity(0,0,0,0.4) at 10 Hz); (c) with balance mode 0 already in effect since entry, the controller itself settles: a few settling steps are by design and are counted by odometry — ignore odometry here; (d) define 'stopped' as GetFsmMode()/sportmodestate.fsm_mode == 0 for 5 consecutive 10 Hz samples (official: 0 = standing/static, 1 = moving/dynamic; also the gate for mode switches); (e) verify final LiDAR distance, one creep-correction burst if short; (f) optionally SetFsmId(802) to park in a velocity-deaf standing state (measured working on this FW), else stay in 200. Never SetBalanceMode(1)/ContinuousGait (documented: keeps stepping at zero — the exact 'sits in front of the wall stepping' symptom you saw at 14:09, and the remote labels it 'not recommended'). Never SetFsmId(4) from 200 (refused while fsm_mode==1; the doc boot path is 1->4->run, not run->4; UNVERIFIED whether it is accepted once static — test once, but the design must not depend on it). Never Damp() as a stop (e-stop, robot collapses). Ramp vs cut: prefer a short ramp (cmd 0.30 -> 0 over 0.3-0.5 s, or simply one tick at 0.30 then zeros — anything in 0<cmd<0.30 is a stepping-in-place band, so the 'ramp' is effectively short: keep the minimum non-zero command at 0.30 and jump to 0 from there). Hold time before parking: until fsm_mode==0, typically 1-3 s; log the elapsed time so the operator can see it.

### 止めた後に後ろへ流れる理由の見立て

Most plausible, in order: (1) A persistent backward velocity bias in the walk controller: your own fit v = 0.4*(cmd-0.10) implies roughly -0.04 m/s at cmd 0, i.e. every second of stepping-in-place after a zero command moves the robot ~4 cm backward; 3-5 s of settling steps = 12-20 cm, plus momentum/lean = the observed 20-50 cm. The remote has explicit trim keys for exactly this ('Offset Compensation: Forward Offset Hold R1+Click DOWN / Backward Offset Hold R1+Click UP' in R1+X/R1+Y; 'Forward/Backward Lean START+UP/DOWN' in R2+A, https://support.unitree.com/home/en/G1_developer/remote_control). Someone may have stored a backward offset; there is no SDK API to read or clear it. (2) Balance mode 1 (continuous gait) left on, either by code (gait_cont) or by the remote's double-click START: the robot then never stops stepping at zero and the bias integrates indefinitely — 'falls backward slowly while stepping' fits this. (3) Cutting a fixed-speed command to zero with no deceleration: the controller catches the body's forward momentum by stepping and then over-corrects backward; the remote's stick decays gradually so it does not show this. (4) Odometry artefact: leg odometry counts stepping-in-place, so part of the 'drift' may be measurement — trust LiDAR only. Avoid: verify GetBalanceMode()==0 after entry; reset/re-trim the offset with the remote and re-measure zero-command drift on flat floor (UNVERIFIED that this is the cause — it is an inference); decelerate to 0.30 before zeroing; keep the last non-zero command >= 0.30 (never in the 0.10-0.25 band where the bias dominates); fold the measured residual drift into stop_margin (stop slightly closer to the wall than nominal) and use the LiDAR creep correction afterwards. If the bias survives all of that, it is a firmware controller bias that only the remote trim or a stop-margin offset can compensate.

### 速度の対応

Fixed, no adaptive learning: v_actual = k*(cmd - v_dead) with k=0.40, v_dead=0.10 from the 2026-09-04 14:08 measurements (0.50->0.15-0.20, 0.42->0.13, 0.35->0.08, 0.20->0.04, 0.15->0.02). Inverse: cmd = v_dead + v_des/k, clamped to [cmd_min_walk=0.30, cmd_max=0.90], i.e. usable actual speed range 0.08-0.32 m/s. Keep calib_learn=False (learning shrank commands and increased backward drift). Store the two constants in walk_calib.json and let the operator re-measure them with a one-shot calibration run (walk 2 m at cmd 0.6, compute k from LiDAR delta / time) rather than online updates. The 0.32 m/s ceiling at cmd 0.9 is the firmware clipping ('The program will automatically set the cropping to the allowed range'); the only documented selector for regular-control speed is the remote's double-click L1 (high) / L2 (low) — UNVERIFIED whether the unit is in low-speed mode; SetSpeedMode 0..3 is documented for run mode only and its effect in 200/501 is unknown. Fix the comments in autowalk.py (line 62) and real_robot.py: G1 valid values are 0..3 = 1.0/2.0/2.7/3.0 m/s, not -1..2 (that is the Go2 SpeedLevel convention).

### 歩容とバランスモード

balance mode (7102): 0 = BalanceStand / remote 'Standing Mode' — 'when the speed command is 0 and the robot is stable, the robot stops stepping and steps only when necessary'; 1 = ContinuousGait / remote 'Keep stepping (not recommended)' (double-click START inside R1+X/R1+Y) — 'continue to step even if the current speed is 0'. Use 0 only, set once while static after entering the walk FSM, verified via _Call(7003,'{}') (no Python wrapper; parse like GetFsmId). fsm_mode (7002 / rt/sportmodestate.fsm_mode): 0 static (mode switching allowed), 1 dynamic (most switches refused) — this is both the 'stopped' signal and the reason SetFsmId(4) is refused from 200 while stepping. FSM map for this unit: 200 = legacy Start() id (SDK before 2025-06-09 C++/2026-04-20 Python), undocumented today but on this FW it enters walking and reads back 501 = 'Walk Motion-3DoF-waist' (regular control for the 29-DoF chassis, remote R1+Y); 500 = 1-DoF-waist regular control, ignored here; 802 = 29-DoF run controller (801 renamed after ai_sport 8.6.x.x), velocity-deaf on this FW (issue #170 identical), usable only as a standing park state and UserCtrl entry; 4 = lock standing without balance control, reachable from damp, not from walking. Add thin wrappers GetFsmMode() and GetBalanceMode() to the vendored client (7002/7003, {"data":int}).

### FW と SDK の版

Tell the operator: the firmware (ai_sport >= 8.6.x.x, service name 'sport', FSM 802 present, likely sw 1.5.x) is NEWER than the vendored Python SDK semantics assume in one direction and OLDER in another. Newer: Unitree renamed Start() to SetFsmId(500) (C++ 2025-06-09 commit 40c02be203, Python 2026-04-20 commit 82d7ddee38), and 500 is the 1-DoF-waist controller — it is silently accepted (code 0) but ignored on 29-DoF units (issue #170, open, no Unitree answer). Return code 0 from any Set* means 'the service replied', not 'the state changed' — always read back. SetSpeedMode is run-mode only (0..3), remove the -1..2 comment. Debug mode (L2+R2) kills the whole high-level service. If the remote is used between runs, the operator must (a) leave walk mode in 'Standing' (not 'Keep stepping'), (b) not store offset compensation, (c) pass through damp (L2+B) before re-entering main control per the manual. ### 距離の制御

Use the LiDAR wall range only (toe-referenced) for the whole final approach; odometry only for the calibration run and as a plausibility check. Let e = d_lidar - stop_dist (stop_dist 0.60 m). Profile per 10 Hz tick: e > 1.5 m: cmd_max 0.90 (v~0.32; braking lead needed = v*(cmd lag ~1.0 s + duration 0.4 s) + settle ~0.2 m ≈ 0.65 m, so start slowing well before). 0.6 < e <= 1.5 m: cmd = v_dead + clamp(0.5*e, 0.08, 0.32)/k, i.e. proportional slow-down down to the creep floor. e <= final_zone 0.60 m: creep at cmd_min_walk 0.30 (v~0.08 m/s, ~7 s for 0.6 m; accept the time — it is the price of a clean stop). e <= stop_margin: zeros. stop_margin = expected forward travel after the zero command (creep 0.08 m/s x ~0.5 s command lag ≈ 0.04 m) minus the measured post-stop backward drift at creep speed (measure 3 trials; if drift is 0.10 m, stop_margin = 0.04 - 0.10 = -0.06, i.e. command zero 6 cm past nominal). Start with stop_margin = +0.08 (current '残り 8cm' value) and tune from the settle logs. Safety: hard stop (zeros) if d_lidar < stop_dist - 0.15 or if the corridor (half_w 0.35) shows a point closer than 0.35 m, if LiDAR is stale > 0.3 s, if fsm_id leaves WALK_FSMS, or if 4.0 m (max_fwd) has been walked without a wall. After fsm_mode==0: single correction burst at 0.30 for t = |e|/0.08 s (cap 3 s) if e > 0.08 m; never correct backward (vx<0 command is untested and the bias already pulls backward). Anchor watch (anchor_s 6 s) stays as a monitor only — do not auto-step to hold position while the bias is unresolved, it re-triggers the stepping loop; instead log the drift.

- UNVERIFIED: root cause of the backward drift (remote offset compensation vs controller bias vs balance mode 1 vs cut-from-speed momentum). The design tolerates it via creep-then-zero and a stop-margin offset, but a bias of -0.04 m/s while stepping cannot be removed by SDK calls; only the remote trim or a stop margin can compensate.
- UNVERIFIED: whether SetFsmId(4) is accepted from 200/501 once fsm_mode==0; documented path is 1->4->run. The design does not depend on it; 802 park is the measured alternative.
- UNVERIFIED: whether the 0.32 m/s cap is the remote's low-speed mode (double-click L2) or a hard firmware clip; SetSpeedMode is documented only for run mode and may do nothing or change the FSM in 200/501 — always read back GetFsmId after trying it.
- Risk: SetBalanceMode(0) sent while moving previously caused a backward walk; the design sends it only when fsm_mode==0 right after entry. If entry lands directly in a dynamic state, wait, do not force.
- Risk: duration 0.4 s with a blocking _Call at 10 Hz — if an RPC takes >0.4 s (SetTimeout 10 s) the robot auto-stops mid-walk (safe but jerky). Use a per-call timeout of ~0.3 s and treat timeouts as a missed tick, not a fatal error.
- Risk: the creep phase at cmd 0.30 (~0.08 m/s) is slow (~7 s for 0.6 m); shortening final_zone below 0.4 m trades stop precision for time. Do not go below cmd 0.30 — the 0.10-0.25 band is the stepping-in-place/backward-bias band.
- Risk: LiDAR yaw/mount errors (yaw_autocal disabled for good reason) shift the wall distance; keep front_offset and the wall-normal check, and reject ranges when the wall fit angle > 15 deg.
- Third-party claims (roboticsknowledgebase: 500 jitter, 1-DoF units losing 501 after fw 1.4.9; GetSoloTech 200 table) are unverified and not relied on.
- 802 as the UserCtrl entry state and the 802->200 direct transition are measured on this unit only (undocumented); keep them behind the existing fw_profile check.
- sport_lease behaviour on this firmware is unknown (issue #170 reports lease apply error 3102 on 1.5.3); keep enableLease=False.
