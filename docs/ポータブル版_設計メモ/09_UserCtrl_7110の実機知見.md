# 9. ★UserCtrl(7110)の実機知見 — 「ACKは嘘をつく」「802からしか入れない」

対象機: **Unitree G1 / 29DoF / FW 1.5.3.8 / ai_sport 8.6以降**
出典: 2026-08-26 実機セッション(12:43〜15:22)の実測。[06_FW世代とSDK.md](06_FW世代とSDK.md) 6.4節を独立文書として再構成。

公開情報(公式doc・GitHub・コミュニティ)を一通り当たったが、以下2件に相当する記述は
**英語・中国語ともに見つからなかった**。両方とも「知らないとロボットを倒す」種類の情報なので、
再現手順と実測値つきで残す。

---

## 9.1 結論(先に2行)

1. **`SwitchToUserCtrl`(7110)は `code=0` を返しながら、実際には何も切り替わらないことがある。**
   戻り値を成功と信じて低レベル指令を流すと、内蔵制御が立位保持を続けたまま
   自作制御が「効いているつもり」で走る。→ **ACKを信じず、必ず所有を実測で確認する。**
2. **当機FWでUserCtrlに入れるのは走行(802)からだけ。** 歩行(500/501)・ロック立位(4)からは
   すべて黙って拒否された。公式テンプレの言う「WALKRUN mode」は歩行ではなく**走行**のこと。

## 9.2 発見1: 7110 は `code=0` を返しながら黙って無効になる

### 前提として先に踏んだ罠(これも公開情報に無い)

**vendored SDK の `LocoClient` は 7110/7111 を API 登録していない。**
`_Call` がロボットへ送信すらせず、クライアント内部で **3103(API_NOT_REG)** を返す(実機12:43)。

```python
# 対策: 自前で追加登録する(登録するだけなら旧FWでも無害)
client._RegistApi(7002)   # SelectMode 等
client._RegistApi(7110)   # SwitchToUserCtrl
client._RegistApi(7111)   # SwitchToInternalCtrl
```

ここを直さないと「7110が動かない」の原因がFW側かSDK側か切り分けられない。
**まず 3103 が消えることを確認してから、以下の議論に入ること。**

### 本題: 送れるようになった後も、ACKは成功を意味しない

| 実機時刻 | やったこと | 返り値 | 実際に起きたこと |
|---|---|---|---|
| 12:48 | `SwitchToUserCtrl({"data": false})` | **code=0** | 関節が1本も動かず、内蔵制御が立位保持を継続 |
| 12:54 | 全パラメータ変種を総当たり | **全て code=0** | 同上。ACKのみ。FSMは1000にならない |
| 13:01 | 501 → `SetFsmId(4)` | 受理 | **8秒間 FSM不変**(501のまま拒否) |

`{"data": false}` のような明らかに無効な引数ですら `code=0` が返る。
**つまり 7110 の戻り値には切替の成否の情報が入っていない。**

### 原因(公式docの一文と符合する)

新FWは `rt/sportmodestate` に `fsm_mode` を配信している:

```
unitree_hg::SportModeState_ { fsm_id, fsm_mode, task_id, task_time }
    fsm_mode = 0  静的  → モード切替可
    fsm_mode = 1  動的  → 切替ほぼ不可
```

**歩行(500/501)は、その場で静止していても `fsm_mode=1`(動的)として扱われる。**
公式docの「状態が不適切なときはモード変更を禁止する」がここで発動し、
**禁止されたことを呼び出し側に伝えずに** code=0 を返している、というのが実測と整合する解釈。

> 目視では「立って止まっている」ので静的に見える。**人間の見た目と `fsm_mode` は一致しない。**

### 対策: 所有確認を3段構えにする

```
1. 7110 を呼ぶ(戻り値は見るが、信じない)
2. 0.1秒後に GetFsmId() == 1000 を確認   ← 公式mimicテンプレと同じ作法
3. ★ウィグル: 1関節だけ微小に動かし、lowstate の実測 q が追従するかを見る
   → 追従しなければ所有できていない。即中止して silence()
4. 実行中も毎秒 GetFsmId を再確認。1000でなくなったら即Exit
```

**手順3(ウィグル)が要る理由**: FSM値の読みだけでは「読めているが効いていない」状態を
弾けない場面があった。**関節が実際に自作指令へ追従することを一度だけ物理で確かめる**のが確実。

## 9.3 発見2: UserCtrl に入れるのは 802(走行)からだけ

### 誤解の系譜 — 「WALKRUN」は歩行ではない

公式mimicテンプレ([unitreerobotics/unitree-app-templates](https://github.com/unitreerobotics/unitree-app-templates))は
**進入は WALKRUN から 7110、FSM1 からはエラー**としており、テンプレのコードは
`fsm_id == 801` でゲートしている。

この "WALKRUN" を **歩行(500/501)** だと読んだために、当機では数時間ぶんの試行が全部空振りした。

```
正しい対応:
  歩行 (walking)  = FSM 500 / 501(腰3DoF)   ← ここからは入れない
  走行 (run)      = FSM 801、ai_sport 8.6以降は 802
                    リモコン R2+A の通常起動がこれ    ← ここから入れる
```

**当機の実測拒否はすべて 501 / 4 / 1 からで、802 からは一度も試していなかった。**

### 実機で試した進入経路の全結果

| 進入元 FSM | 結果 | 実機時刻 |
|---|---|---|
| 500 / 501(歩行) | code=0 を返して**黙って無効**(fsm_mode=1 動的扱い) | 12:48 / 12:54 |
| 4(ロック立位) | そもそも 501→4 の遷移自体を**拒否**(8秒不変) | 13:01 |
| 1(ダンピング) | **成功するが脱力窓 0.27秒**が発生(予備経路) | — |
| **802(走行)** | **成功。FSM=1000 を確認。往復も実証** | **15:22** |

### 成功した手順(15:22)

```
1. 501(歩行) → 802(走行) へプログラム遷移      ← ここは通る
2. 802 のまま静止立位になるのを待つ
3. ★latch(現在の実測姿勢を目標として凍結)して rt/user_lowcmd へ事前ストリーム開始
   → 切替までロボットは user_lowcmd を無視するので、競合窓は原理的にゼロ
4. SwitchToUserCtrl(7110)
5. GetFsmId() == 1000 を確認 + ウィグルで所有確認
6. (復路) SwitchToInternalCtrl(7111)  復帰モード 0=LAST / 1=PASSIVE / 2=WALKRUN
```

**手順3の「切替前から流しておく」が `release` 方式との決定的な差**で、
`ReleaseMode` 方式の競合窓 0.20秒(旧FW)〜0.50秒(新FW、実機12:35)が**ゼロになる**。
→ 詳細は [02_受け渡し問題_実機の核心.md](02_受け渡し問題_実機の核心.md)。

### 802 に近づくときの罠(実機13:58)

**ロック立位(4)からは走行へ自動遷移しない。**
`SwitchToInternalCtrl` の復帰モード **WALKRUN(2)** を指定したところ、
当機ではこれが **802(走行)** に入り、**吊った機体が空中で走行動作を始めて暴れた**。
さらに **ゼロトルク(FSM 0)への遷移も 802 から拒否**され、止める手段が一瞬なくなった。

> **802 は「静止立位に見えても走行制御が走っている状態」**である。
> 進入元として使うが、**吊り状態でここに入れるときは必ずリモコンE-stopを握っておくこと。**
> 通常復帰は **LAST(0)** を既定にし、非常時のみ強制 PASSIVE(1) にしてある
> ([04_安全設計と調整値.md](04_安全設計と調整値.md))。

## 9.4 実装として落とし込んだ形

```
config「安全.受け渡し方式」
    "release"  … MotionSwitcher の ReleaseMode(既定・旧FW/新FW両対応・実績あり)
    "user"     … 7110/7111(新FWのみ。旧FWと判別されたら起動時に中止)

config「安全.ダンピング経由のUserCtrl進入」 = true   ← 802 が使えないFW向けの予備経路
config「安全.UserCtrl復帰モード」          = 0(LAST)
config「確認秒数_user進入」                = 0.0     ← 切替の瞬間から方策が制御(静的保持を挟まない)
```

**`確認秒数_user進入 = 0.0` の根拠**: 切替後に静的保持で様子を見ようとすると、
その保持中に後傾が **3度 → 13度** に成長した(実機14:24)。
公式mimicテンプレも「切替の瞬間からRL方策が制御」で静的保持の時間を持たない。**同じ方針に合わせた。**

## 9.5 世代判別の注意(この知見を他機で再現するとき)

FW世代の判別は **ロボットに一切指令を送らず、読むだけ**で行うこと。

- `rt/sportmodestate` を1.5秒購読 → 届けば新FW
- 届かなければ `GetFsmId`(7001)。**200=旧FW** / 500,501,801,802=新FW
- 決め手なし → **旧FWとして振る舞う**(実績側に倒す)

> ★実測 2026-08-26: **FW 1.5.3.8 では `rt/sportmodestate` と `rt/user_lowcmd` が配信されているのに、
> 自前定義IDLでの購読はデータが来なかった**(実物の型と構造が合わず黙って不成立)。
> vendor版SDKには go 側の別物しか無いため hg 型を自前定義したが、それでも合わない。
> → **型の中身に依存しない「DDS組み込みトピック(DcpsPublication)でのトピック名の発見」**が
> 最も確実な新FWの証拠になる。

ここも「黙って不成立」というパターンで、**7110のACK問題と同じ性質**である。
**このFW世代は、失敗を失敗として返さない箇所が複数ある**と考えて設計した方がよい。

## 9.7 未検証(正直な申告)

- **802 経由の UserCtrl で着座を通した実績はまだない。** 往復が実証されただけ(実機15:22)
- 最初の実機試験は **必ずハーネス + 片手にリモコンE-stop**([08_未解決課題と次の一手.md](08_未解決課題と次の一手.md) 8.3-4)
- 歩行(500/501)からの直接進入は、**FW更新で有効になる可能性がある**
  (公式テンプレの第1段がそれを前提にしているため)。更新のたびに再試験する価値がある
- ここに書いた挙動は **FW 1.5.3.8 / ai_sport 8.6 系での実測**であり、他世代での再現は未確認
