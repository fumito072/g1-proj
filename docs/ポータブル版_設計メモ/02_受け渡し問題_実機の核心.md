# 2. ★制御権の受け渡し — 実機で起きたことの核心

このパッケージの実機知見の8割はここに集中している。
「学習方策が悪い」のではなく、**内蔵制御(歩行モード)から自作制御へ制御権を渡す
数百ミリ秒**で毎回ロボットが乱され、方策が一度も正常に始まらなかった、という話。

## 2.2 やって**失敗した**対策(記録として重要)

### 案A: 解放前に `follow` のまま kp をランプする(prearm)
**誤り。** `follow` は毎周期 目標を現在姿勢に更新するので**偏差は常にゼロ**。
つまり **kp をいくら上げても復元トルクはゼロ**(効くのは減衰 kd だけ)。
沈みが66度→7.6度に減ったのは kd の減衰効果だけだった。

### 案B: 内蔵制御を「静止」させてから解放する
| 試したこと | 実測結果 |
|---|---|
| `StopMove()` + `SetBalanceMode(0)` | 静止せず**後ろへ歩き出した**(角速度 1.074 rad/s) |
| `SetFsmId(4)`(スタンドロック) | 遷移そのものを**拒否**(FSM=200のまま) |

原因: `StopMove()` の実体は `SetVelocity(0,0,0)` で、これは「停止しろ」ではなく
**「その速度で動け」という動作指令**。ゼロでも歩容制御には動作命令になる。
`SetFsmId(4)` は元の一式のREADMEにある手順だが、読み直すと
**吊った状態での初回セットアップ専用**で、実際の着座実行(実機27本の運用)では
使われていなかった。

> この失敗の副作用で「歩行モードのまま戻らない」状態が残り、
> 救済ツール `restore_walk_mode.py` が作られた(SetVelocityを一切送らずに
> SelectMode("ai") → FSM 200 → SetBalanceMode(1) を順に行う)。

### 案C: 重力補償トルク(gravity feedforward)を入れる
2案とも検証で不成立。

| 案 | 結果 |
|---|---|
| 空中(qpos[2]を高く)で `mj_inverse` | **脚6関節すべて符号が逆**。左足首 真値+13.40Nm に対し **−0.14Nm**(1/100) |
| 両足を接地させて `mj_inverse` | MuJoCoが接触拘束に荷重を配分し**全関節ゼロ** |

そもそも立位保持に要る真のトルクは脚・腰で最大16Nm、kp=400なら位置誤差
16/400 = **2.3度**にすぎない。実測でもPDのみで4秒保持した定常誤差は
**脚・腰1.74度・体幹ピッチ3.5度**。実機で起きていたのは15度→31度の転倒で
**桁が2つ違う**。→ 配線(`motor_cmd.tau`)だけ残し、値は常にゼロ。

### 案D: ENGAGE中に「傾いたら止めて待つ」
**静止して待つ方が不安定だった。** MuJoCo実測: 9度後傾した状態で目標を止めたまま
保持すると **0.60秒で25度超、0.76秒で35度**。実機13:25のログとも符合。
→ 移動を止めず、危険なら即中止する設計に変更。

## 2.3 公式ドキュメントによる裏付け(2026-08-24 夜の4方向調査)

Unitree公式 quick_start:
> 電源投入後、内蔵モーションコントロールは(リモコン操作がなくても)速度0の指令を
> 周期送信し続ける。この状態でSDKを使うと**命令競合でG1がジッタする**

つまり:
- 「ががが」= `rt/lowcmd` と内蔵制御の**命令競合そのもの**(公式の言うジッタ)
- **ゲインゼロのフレームでも競合する**(15:42の実測)
- 実績27本の操縦盤が「純正所有中は**完全無送信**」を不変条件にしていた理由がこれ
- **重複送信が許されるのは「偏差×時間」が小さいときだけ**:
  静止確認済み + 指令=現在実測姿勢(偏差ゼロ) + 窓0.5秒以下。ゲインの大小は無関係

### 実装した機械的保証: 送信スレッドの「所有フラグ(owned)」
- `latch()`(受け渡し)で owned=True、`silence()`(返却/中止)で False
- **未所有のあいだは1フレームも出ない**。非常時の脱力ストリーム(kd=2)も未所有では発火しない
- 解放失敗・返却後・静止待ち中止など、**全ての失敗経路が silence() で終わる**

## 2.4 最終的な正解の手順(実機27本の運用実績に合わせた)

```
0. ★静止待ち(観測だけ。指令は送らない)
   角速度 < 0.25 rad/s かつ 脚の関節速度 < 0.4 rad/s が 0.6秒 続くこと(上限15秒)
   止まらなければ何もせず中止 → オペレータがリモコンで足踏みを止める
1. いまの姿勢を掴む(latch)。★最初からフルゲイン(kp400)。ランプ不要
2. 送信が流れているのを確認(0.3秒)
3. ReleaseMode          ← 内蔵制御(FSM/歩容/バランスモード)には触れない
4. 解放を確認。目標はもう固定・フルゲインなので、そのまま支えている
5. 掴んだ姿勢 → 参照の初期姿勢へ姿勢合わせ(ENGAGE)
   20度/秒・最短2.5秒・最長6秒。傾きが20度を超えたら即中止
6. 立位保持の確認・バランス保持(方策を参照凍結で回す安全網)
7. 参照を進める
```

**設計の芯は「目標を凍結してから解放する」**。
- 合成テスト: 旧い順序(解放後に凍結)= 沈み **+37.8度** / 新しい順序 = **0.0度**
- 実機: 沈み込み **66度 → 7.6度 → 0.1度**(修正のたびに縮んだ)
- ランナーは解放中の沈み込みを毎回ログに残す(0.15rad超で警告)

### なぜ手順0(静止待ち)が要るか
歩行モードは絶えず足踏みを続けている(実測 角速度 1.07〜1.65 rad/s)。
その最中に掴むと**片足が浮いた瞬間の姿勢を凍結**しかねず、凍結した単脚支持は必ず倒れる。
SDKから歩容を止める手段は無い(2.2の失敗2件)ので、リモコンで止めてもらい、
こちらは観測だけで静止を確認する。
しきい値の根拠: 実機27本の立位は角速度0.07rad/s前後、足踏み中は1.0超 → **0.25で明確に区別**。

### 「戦いの窓」を0.15秒に潰す
14:34/14:35/15:33 の2秒の内訳は **SDKクライアントの初期化とモード確認**だった。
これらを掴みの**前**に使い切り(`prepare_release()`)、`latch → 即 ReleaseMode` にした。
内蔵と重なる窓は ReleaseMode 1往復ぶん = **合成テスト実測0.15秒 / 実機0.20秒**。

ログには毎回「**掴み→解放の窓 X.XX秒**」「**解放直後の傾き X度**」が出る。次回はこの2つを見る。

## 2.5 しきい値の見直し(元の一式の実績値に合わせた)

| | 従来 | 現在 | 根拠 |
|---|---|---|---|
| 転倒とみなす傾き | 0.45rad = 25.8度 | **0.61rad = 35度** | 一式 `TILT_POLICY_DEG=35` |
| 脱力に切り替える傾き | 転倒と同じ | **0.80rad = 46度** | 同値だと傾き中止の瞬間に必ず脱力していた(実機11:38 pitch−0.45で脱力) |
| ENGAGE中止 | 静止して待つ(8度) | **20度で即中止** | 静止保持そのものが不安定 |

事前検査の脚の判定も、参照 `ref_q` ではなく**シムで方策が実際に取る姿勢**
(`expected_*.npz` の `q_med`)と比較するよう変更。方策は残差方策なので参照から
最大0.7radずれるのが正常で、参照基準だと正常なのに毎回止まっていた(実測0.32rad > 許容0.15rad)。

## 2.6 この回で「検証済み」なのは2点だけ(正直な申告)

1. **latch を ReleaseMode の直前に置く** — 実機で沈み込み 66度 → 7.6度 → 0.1度
2. **内蔵制御に指令を送らない** — 後退歩行とモード切替不能の回帰を除去

**未検証**: 受け渡し後の傾きが実際どこまで収まるか。15度→31度の転倒が latch順序の
修正だけで消えるかは**まだ分かっていない**。残っていれば原因は受け渡しではなく
「内蔵バランスが**動的に**立たせていた姿勢を凍結したこと」そのもの(=倒立振子)なので、
バランス保持を受け渡し直後へ前倒しするなど別の対策が要る。
