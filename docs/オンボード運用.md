## 1. なぜオンボードなのか — 無線でPC制御はできない

**機体のDDSサービスは eth0 にしかバインドしていない。**

```
eth0  → 239.255.0.1 (DDS探索マルチキャスト) に参加 ✓
wlan0 → DDS系マルチキャストグループ なし ✗
```

PC側で `cyclonedds.xml` にユニキャストのピア指定を入れて試したが
**lowstate 受信 0**。PCのIPを機体の設定値(192.168.179.24)に合わせても同じ。
PC側の問題ではなく、機体が無線にDDSを出していない。

→ **無線運用の唯一の道がオンボード実行。** 制御はDDSごと機体内で閉じ、
UIだけがWi-Fiを渡る。通信が切れても制御は止まらないので、PC制御より安全側。

50Hz制御をWi-Fi(ジッタ11ms・最大56ms)に載せないで済むという意味でも正しい。

## 3. ★制御周期が14Hzに落ちる — LowStateはポーリングで読む

**症状**: 方策開始1秒で `★DAMP: 制御周期が遅い: 中央71ms = 14Hz`。

**原因**: `ChannelSubscriber.Init()` に handler を渡すと、SDKは DataReader に
`Listener(on_data_available=...)` を付ける。すると cyclonedds のC側受信スレッド
(`recvMC`)が **1043回/秒 Python に入ってGILを握り**、同じプロセスの50Hz制御
ループを餓死させる。**PC(x86)は単スレッド性能が高く表面化しない。機体でだけ落ちる。**

同じ原因で `SwitchToUserCtrl` の切替も通らなくなる(RPC応答処理が回らず
`GetFsmId` が None を返す)。**一見別々の2症状が同じ根を持っていた。**

**対処**: `Init(None, 0)` で Listener を付けず、専用スレッドが `Read()` を
約180Hz(sleep 5.5ms)でポーリングする。`Read()` は `take_one()` で、履歴QoSが
KEEP_LAST(1) なので**溜まった古いサンプルではなく常に最新**が返る
(検証: tick差分の中央が 5 = 1043/180 で追従遅れなし)。遅れは最大5.5ms。

```
                recvMC   プロセス全体   制御周期
Listener方式     76%        87%      中央71ms(14Hz) → 自動DAMP
ポーリング方式    2%        41%      中央20.4ms(49Hz)・25ms超え16% → 395コマ完走
```

PC実績の「25ms超え24%」より**良い**。

★受信途絶の監視 `_last_state_t` はポーリングのたびに更新すること。この
スレッドが例外で死ぬとLowStateが止まり自動DAMPになるので、例外は必ず内部で捕まえる。

## 4. ★参照npzを開いたまま制御ループへ渡さない

**症状**: `BadZipFile: Overlapped entries: 'ref_xy_abs.npy' (possible zip bomb)`
で制御ループが落ちる。run001は完走してrun002で出る、という確率的な出方をする。

**原因**: `Policy` が `np.load()` の返す **NpzFile(開いたままのzip)をそのまま
保持**し、`ref_xy_abs` などを50Hzの制御ループから毎コマ遅延展開していた。
NpzFileはスレッド安全でなく、共有ファイルハンドルへの読みが交錯すると
zipfile の zip爆弾ガードが誤発火する。毎コマ解凍するぶん制御周期も食う。

**対処**: 読み込み時に全配列をメモリへ展開してzipを閉じる(`_Ref` クラス)。
`.files` も生やしてあるので既存の呼び出し箇所はそのまま動く。

## 5. ★Python 3.8 では `__file__` が相対パス

機体は **Python 3.8.10 固定**(Jetson L4T / Ubuntu 20.04)。PC側は3.10。

**Python 3.9+ は `__file__` を絶対パス化するが、3.8 は相対のまま。**
そのため `Path(__file__).parent.parent` が `.` に潰れ、`ROOT / "deploy"` が
見つからず `FileNotFoundError: 'deploy'` で起動失敗する。**PCでは同じコードが
動くので気づきにくい。**

**対処**: `Path(__file__).resolve().parent` と必ず `.resolve()` を挟む。
real/ の8ファイルを修正済み。新しくスクリプトを足すときも同様に。

なお `preflight.py` が「Python 3.10以上が要る」でNGを1件出すが、機体では3.8で
実運用できている(推論14ms / 制御49Hz)ので、機体上ではこのNGは想定内。

## 6. ★UserCtrl の切替確認は6秒待つ

**症状**: `SwitchToUserCtrl(7110) → code=3104 (3.00秒)` のあと
`★FSMが1000にならない(いまNone)`。

**原因**: `SwitchToUserCtrl` のACK(code)は**元々成否を表さない**とコード内に
明記されている。実際の判定は「その後 FSM=1000 になるか」だけで、その窓が
2.0秒しかなかった。オンボードではCPU競合(§3)で2秒に収まらない。

**対処**: `USER_CTRL_CONFIRM_S = 6.0` へ拡大し、途中経過をログに残す
(`?` = GetFsmId が RPC不達)。§3のポーリング化と併せて、いまは0.1〜0.2秒で通る。
この窓の間に出しているのは user_lowcmd のストリームだけで、UserCtrlに入るまで
ロボットは無視するので、延ばしても機体は動かない。

## 7. UIの応答性(無線)

### 7-1. ボタンが10秒返らない → `"?"` と `"(解放中)"` を区別する

`current_mode()` は CheckMode RPC が2.5秒でタイムアウトすると `"?"` を返す。
`_select_ai` がそれを `"(解放中)"` と同一視して6秒粘り、続けて呼び出し元の
RPC(4秒)が走るので、**最大10秒**ボタンが返らなかった。その間 `busy` なので
他のボタンも全部「処理中です」で弾かれ、操作不能に見えていた。
**コントローラーで歩かせた直後**はloco側が忙しくCheckModeが遅れるため必ず嵌まる。

**対処**: 探りの timeout を0.8秒に。`"?"` が2回続いたら粘らずに指令を送る
(読めないことは「解放されている証拠」ではない)。**最大10秒 → 約1.6秒**。

### 7-2. Keep-Alive とペイロード削減

UIは `/state` を5回/秒 + beat を1回/秒 = **6接続/秒を張り直していた**
(BaseHTTPRequestHandler の既定は HTTP/1.0)。ロスのある無線ではSYNが落ちる
たびに1秒以上の再送待ちになる。

- `protocol_version = "HTTP/1.1"` で Keep-Alive 有効化(`_send` は元々
  Content-Length を送っているのでそのまま切り替えて安全)
- `patterns`/`notes`/`warn` は起動中不変なのに毎tick送っていた。起動時に
  `?meta=1` で一度だけ取ってJS側でキャッシュ → **ペイロード 10904B → 2790B**

### 7-3. ★Wi-Fiの省電力を切る

**ロス0%なのにRTTだけ174〜247ms**、という症状が出たら省電力モードを疑う。
ビーコン間にスリープするため、電波が弱いほど遅延が乗る。

```
Power save on  → UI /state 中央33ms・最大128ms
Power save off → UI /state 中央26ms・最大 52ms   ※信号は -56→-69dBm と悪い条件で
```

`wlan0-nopowersave.service` を作成・enabled 済み(起動時に自動で無効化)。

### 7-4. ハートビート

UIは1秒ごとに beat を打ち、途絶するとDAMPする(操作者がUIを失った状態で
走らせ続けないため)。**既定を 3.0秒 → 8.0秒** に延ばした。有線前提の値では
無線の瞬断で誤作動する。監視が効くのは方策実行中と `custom_active` のときだけで、
標準モード中(`STD:*`)は内蔵制御が支えているので監視しない。

★**ブラウザは前面に置くこと。** 背面タブだと `setInterval` が抑制され
(Chromeは最小1回/分)、猶予をいくら延ばしても途絶する。

## 8. ネットワーク構成

| | 値 |
|---|---|
| 機体 wlan0 | **192.168.179.100/24**(SSID `SPW_X11_fce0f9`、モバイルルーター ERC109) |
| 機体 eth0 | 192.168.123.164/24 |
| PC(推奨) | 192.168.179.24 ← 機体の `~/cyclonedds_ws/cyclonedds.xml` がこのIPを決め打ち |
| SSH | `unitree` / パスワード `123`(sudoも同じ) |

**無線が繋がらないときの最有力容疑者**: `/var/lib/NetworkManager/NetworkManager.state`
の `WirelessEnabled=false`。NetworkManagerがこれを保存していると、起動のたびに
rfkillで無線チップをソフトブロックする。wlan0自体は netplan/networkd 管理
(NMからは unmanaged)だが、**無線のON/OFFという全体スイッチはNMが握っている**
ため、wpa_supplicant をいくら追っても解決しない。
→ `sudo nmcli radio wifi on` で `WirelessEnabled=true` が保存され恒久的に直る(適用済み)。

## 9. 有線ケーブルの扱い

制御には**一切影響しない**(オンボードなので機体内で完結。ケーブルを抜いた
状態でUIから「立つ」まで通ることを実測済み)。

| 場面 | 有線 |
|---|---|
| コード同期・再起動・デバッグ | **挿す**(無線でのrsyncは実際に失敗する) |
| **方策の実走** | **抜く**(動作中にケーブルが引っ張られる/引っ掛かるのが物理的に危険) |

★ネットワークは安全経路ではない。UIのdampボタンも通信が切れれば押せない。
**本当の安全装置はリモコンのE-STOP**(ハードウェア・ネットワーク非依存)。
