# G1コックピット 使用手順書

deployの方策を実機G1で走らせる操縦システム。ブラウザから
パターン選択・開始・フェーズ送り・緊急停止を行う。
実機なしでも `--sim` で全機能を結合試験できる(MuJoCoモック)。

---

## 1. 事前準備

### 1-1. 操縦PC(実機と有線LAN接続)

```bash
# Python 3.10+、依存パッケージ
pip install torch numpy mujoco opencv-python unitree_sdk2py

# ネットワーク(docs/REAL_ROBOT.md の実測どおり)
sudo ip link set enp46s0 up
sudo ip addr add 192.168.123.222/24 dev enp46s0
ping 192.168.123.161        # 実機に到達すること(実測0.1ms台)
```

このリポジトリ一式(特に `deploy/` と `model/`)を操縦PCに置く。

### 1-2. 実機側

- 吊り具(ガントリー+ハーネス)に必ず接続。物理E-stopを手元に
- 段差・椅子を設置し、**段の手前の開始立ち位置を床にマーキング**
  (自己位置は脚オドメトリ基準のため、開始位置合わせが重要。許容は±3cm/ヨー±15度)
- リモコンで実機をゼロトルク/dampにしておく(コックピットが接続時に
  MotionSwitcherのReleaseModeで標準制御を解放する)

## 2. 起動

```bash
# まずは必ずシムモックで手順を練習する(実機不要)
python3 real/cockpit.py --sim

# 実機(NIC名を指定)
python3 real/cockpit.py --iface enp46s0
```

ブラウザで **http://localhost:8090** を開く。
画面上部に [SIMモック]/[実機] と表示される。

## 3. 画面の見方

### ロボットモード(Unitree標準制御/SDK経由)

| ボタン | 動作(SDK) | 用途 |
|---|---|---|
| ゼロトルク | LocoClient FSM 0 | 全モータ脱力(吊り具で保持した状態で) |
| ダンプ | LocoClient Damp(FSM 1) | 制動つき脱力。安全な待機状態 |
| 立つ | LocoClient FSM 4 | 標準制御で立ち上がり→バランス立位 |
| ウォーキング | LocoClient FSM 200 | 運用制御(標準の歩行・バランス) |
| カスタム制御へ | ReleaseMode+送信再開 | 診断用。通常は押さない(下記★) |

★排他制御: 標準モードのボタンを押すと**こちらの500Hz送信は自動停止**し、
制御サービスを復帰(SelectMode)してSDK経由で指令する。
標準モード中のE-STOPはSDKのDampが送られる。

★★**[カスタム制御へ] は Unitree純正のバランスモードではない。**
やっているのは「現在角度 q_now を目標にした関節PD」だけで、重心制御・
接触制御・踏み出し・重力補償は**無い**。切替直後は目標=現姿勢なので比例
トルクはほぼゼロ、純正が出していた支持トルクは引き継げない。
**押した状態で放置すると、指令が正しく届いていても数秒で沈む・傾く。**
通常運用では押す必要がない — [1. ARM] / [▶ 単体実行] が、方策の準備を
全部済ませてから引き継ぎ、引き継いだ直後に方策を開始する。
押すなら、支えたまま速やかに方策を開始するか [ダンプ] へ戻すこと。

★**シームレス引き継ぎ(脱力なし)**: スタンドロック等の標準制御状態から
方策へ移るとき、コックピットは次の順序で制御権を取るため**脱力しない**:
  1) 現在の関節角を読む → 2) 「現姿勢を保持する指令」で先に500Hz送信を
  開始 → 3) それから ReleaseMode で標準制御を解放。
  解放の瞬間から当方のPDが同じ姿勢を保ち続ける(逆順=先に解放すると、
  解放〜初回指令の間モータが無支配になって脱力する)。
  [カスタム制御へ]/[▶ 単体実行]/[START]のいずれもこの手順で引き継ぐので、
  **スタンドロックのまま直接 [▶ 登壇] を押してよい**。
(simモックでは ゼロトルク/ダンプはゲイン近似、立つ/ウォーキングは
現姿勢PD保持の近似=バランス制御なし)

### タスク単体実行ボタン

各パターン選択の右にある **[▶ 登壇] [▶ 旋回] [▶ 座る]** で、
そのタスクだけを現在の状態から実行できる。
- ロボットが直立していれば(傾き<20度)**方策を直接開始**する。
  前のタスクの終端姿勢からそのまま次を押してよい(ハンドオフの姿勢ずれは
  学習済み。補間を挟む方がかえって危険なので挟まない)
- 姿勢が崩れているときだけ開始姿勢へ1.5秒補間する(実機では支えること)
- 完了後は**方策が最終姿勢を維持し続ける**(HOLD。方策なしのPD保持は
  数秒で倒れるため、待機中もバランスは方策が取る)

動作実績(シムモック、2026-08-20): [▶ 登壇]→ホールド(傾き13度)→
[▶ 旋回]→ホールド(8度)→[▶ 座る]→着座維持15秒(26度)を連続で確認。

### 使える判定は1つだけ:「走行中の最大傾き」

```
完走 20.8 〜 32.8 度        参照軌道の最大傾きは 18.0 度
転倒 34.6 〜 39.4 度  (全部40度の自動DAMPで切れている)
                ↑ 33〜35度の間に境界がある
```

**★走行中に33度を超えたら、その回はもう戻らない。**

### 開始前の値では勝敗を予測できない(実測で確認済み)

脚腰15軸の角度・姿勢・角速度・トルク・温度・電圧・制御周期を完走3本と
転倒8本で比較したが、**すべて重なっていて区別できない**。
唯一の系統差は右足首ピッチが転倒回で平均0.041rad(2.3度)深いことだけで、
完走12:32(-0.463)と転倒13:13(-0.432)が逆転しているので決め手にならない。

→ **勝敗はログに写らない物理側(椅子・段・足の位置関係)で決まっている。**

### 参照が想定している設置寸法(MJCFから算出)

| 測る場所 | あるべき値 |
|---|---|
| 段の面の高さ(床から) | **0.210 m** |
| 座面の高さ(段の面から) | **0.378 m** |
| 座面の高さ(床から) | **0.588 m** |
| 足の位置から座面中心まで(後方) | **0.324 m** |

**この方策は「その場でしゃがむ」のではなく「32.4cm 後ろへ下がりながら座る」。**
椅子が想定より前/後ろ/低いと、降りた先に座面が無く前へ抜けて倒れる。

運動学で確認した実測: 実機は毎回**参照より速く沈む**。転倒した13:33は倒れた
瞬間に骨盤が0.452m(参照の着座終端0.454m)まで達していた。
= 高さは合っているのに前傾しながら降りており、座面に乗っていない。

### 許容範囲(手順書より)

自己位置は脚オドメトリ(開始マーキング基準)で、**許容は ±3cm / ヨー±15度**。
方策は椅子を見ていないので、この範囲を機械的に保証するしかない。

## 3-2. 接地の数値確認(2026-08-26追加)

**G1のLowStateに足裏の力センサは無い。**代わりに次の2つで判定する。

### 常時表示(擾乱なし。画面上部のタイル下に出る)

| 指標 | 意味 | **基準値** |
|---|---|---|
| **膝トルク合計** | 両膝の保持トルク。体重が足に乗っているほど大きい | **20〜40 N·m**<br>実測: 完走時 27.0 / 30.9、転倒時 33.4 |
| 足首ピッチ合計 | 前後の釣り合い(CoMが足首の前後どちらにあるか) | 実測: 完走時 +2.4 / +5.9、転倒時 +4.9 |

★膝トルクが 20 N·m を大きく下回るなら、**体重が吊り具に逃げている**疑い。

### [⚖ 接地チェック](能動的。足首を2.9度だけ動かす)

両足首ピッチに **0.05 rad (2.9度)** の指令を入れて、どれだけ素直に動くかを測る。
他の関節は現姿勢で保持したまま(`check_authority` と同じ流儀)。

| 追従率 \|Δq\|/0.05 | 判定 | 物理的な意味 |
|---|---|---|
| **< 0.30** | **接地OK** | 足首を回すと体を傾けることになるので動けない。0.05rad×kp40 = 2N·m は重力トルク(20N·m台)に対して小さい |
| 0.30〜0.60 | △微妙 | 片荷重・縁乗りの疑い |
| **> 0.60** | **★浮いている疑い** | 足(約0.5kg)だけが軽く回っている＝踏む相手がいない |

### なぜこれが要るのか(2026-08-26の実測)

転倒した回と完走した回で、**足首への指令はほぼ同じなのに応答が違った**:

```
右足首ピッチ  実測角度の推移(最初の0.9秒)
  転倒 13:13   -0.43 → +0.10   0.53rad(30度)動いた → τ +18 → -0.1 に消えた
  完走 12:32   -0.46 → -0.20   0.26radしか動かない → τ +18〜+22 を維持
可動域は -0.87。どちらも限界には当たっていない = 関節が詰まったのではなく
**踏む相手がいなかった**
```

方策は「両足が床を踏んでいる」前提で学習してある。体重が吊り具に逃げていると
足首・膝の指令は物理的に意味を持たず、観測も学習時と違う分布になる。

**手順**: `[⤓ 開始姿勢へ]` → `[⚖ 接地チェック]` → 両足とも「接地OK」→ `[▶ 座る]`

## 3a. 実機ミラー(twin.py) — 実機の動きをシミュレータに映す

```bash
# コックピットとは**別のターミナル**で起動する
python3 real/twin.py --iface enp46s0                    # ライブ
python3 real/twin.py --replay logs/real/<session>/run01_0_sit_up_rc_r2.npz  # 再生
```

起動するとコックピットの「ビュー」枠に自動で出る(単独では :8091)。

| 画面 | 中身 |
|---|---|
| 左 | **実機の実際の姿勢** — エンコーダ29軸 + IMU をFKでモデルに反映 |
| 右 | **方策が意図した姿勢** — 参照軌道 `ref_q[t]`。コックピットの進行に追従 |

数値で3つの誤差が出る。**これが「修正につなげる」ための量。**

| 量 | 意味 | 見方 |
|---|---|---|
| 追従誤差 `\|q − target\|` | 指令したのに来ていない量 | **0.35radを超え続ける**ならPDが負けているか関節マッピングの取り違え |
| 参照との差 `\|q − ref\|` | 方策がactionで意図的に付けたずれを含む | 0.70radが構造的な上限。張り付いていればaction飽和 |
| 指令ずれ `target − ref` | 方策が参照からどれだけ離す判断をしたか(≒action×0.7) | 符号つき |

★**必ず別プロセスで動かすこと。**コックピット本体は50Hz制御ループと
500Hz送信スレッドを抱えており、MuJoCoの描画(OpenGL。GILを握る)を同居
させると送信が途切れうる。twin.py は `rt/lowstate` を購読するだけで
**1バイトも送信しない**(`watch_live.py` と同じ方式)。落ちても固まっても
実機の制御には影響しない。

★**これは運動学のミラーであって物理ツインではない。**姿勢は映すが力は
映さない。既定のシーンはロボットと床だけ — 実機の水平位置は分からない
(脚オドメトリはドリフトする)ので、椅子や段差と並べると「座っているように
見える」嘘が混ざる。家具込みで見たいときだけ `--scene task`。

## 3b. テレメトリの見方

- **E-STOP(赤い大ボタン/スペースキー)**: 即damp(kp=0, kd=5)。いつでも押せる
- タイル: **FSM状態** / 傾き(40度で自動damp) / 関節速度RMS / 受信健全性
  (LowStateが0.2秒途絶えると自動damp)
- シーケンス構成: 登り・旋回・着座のパターンをプルダウンで選択
  (推奨初期値: climb_slow_r2 / turn_wide_r2 / sit_up_r2。"(skip)"でフェーズ省略可)
- 進行モード: **ステップ**(各フェーズ開始前に[NEXT]で操作者確認。既定)/ 自動
- 進行状況: フェーズ列・進捗バー・コマ番号
- ログ: 全イベント(ファイルにも `logs/real/cockpit_*/` へ毎コマ記録される)

## 4. 実行手順(実機)

1. **[1. ARM]** — 選択した方策を読み込む(まだ動かない)
2. ロボットを床マーキングの開始位置に**普通の両足立位**で立たせる
   (蒸留済み方策は両足立位からの開始に対応。10/10完走で実測済み)
3. **[2. START]** — 確認ダイアログ後、現在姿勢→両足立位へ1.5秒補間
   (既に立位なら省略)。ステップモードではここで立位待機になるので、
   姿勢を確認して **[▶ NEXT]** で最初のフェーズ開始
4. ステップモードではフェーズの間で停止して待つ。姿勢・吊り具・
   椅子との位置関係(許容±3cm/±15度)を確認して **[▶ NEXT]**
5. 全フェーズ完了後は **HOLD**(最終姿勢で保持)。終了するときは[damp]
6. 異常時: E-STOP → 吊り具で保持 → 原因確認 → 再度ARMからやり直し

★注意: 方策が動いていない間のPD保持は、両足立位でも数秒で釣り合いを
失う(モックで実測)。**待機中(START前・NEXT待ち)は操作者が軽く
支えること**。simモックでは待機中の物理を自動で凍結する。

シムモックのときのみ **[1.5 (sim)配置]** ボタンが出る(モデルを開始位置へ
テレポート)。実機では物理的に置くこと。

### 動作実績(シムモック、2026-08-20)

- 自動モード: climb_slow_r2 → turn_wide_r2 → sit_up_r2 通し完走・HOLD到達
- ステップモード: 両足立位スタート → 各フェーズ間で確認 → 通し完走
- いずれもフェーズごとのログ保存(`logs/real/cockpit_*/`)を確認

## 5. 安全仕様(自動)— 2026-08-26改訂

| 条件 | 見ている場所 | 動作 |
|---|---|---|
| E-STOP/スペースキー | **HTTPスレッドから直接**(キューを経由しない) | 即damp。実測1.5ms |
| 体幹の傾き > 40度 | 監視スレッド(100Hz)+ 制御ループ(50Hz) | 即damp |
| 関節速度 > 32rad/s | 同上 | 即damp |
| LowState途絶 > 0.2秒 | 同上 | 即damp |
| **lowcmd送信の停止 > 50ms** | 同上 | 即damp |
| 観測/方策出力のNaNが3コマ連続 | 制御ループ | 即damp |
| 制御ループの例外 | 制御ループ | 即damp |
| サーバ終了(Ctrl+C) | main | dampを**送り切ってから**終了 |
| **UIハートビート途絶 > 8秒** | 機体側 watchdog(100Hz) | ★2026-09-04 改訂: **dampしない**。方策の実行中は最後まで実行して方策で保持 / 方策なしのPD保持なら内蔵バランス制御へ返して静止 / 歩行は速度ゼロ(docs/通信途絶時の安全設計_20260904.md) |

★**UIハートビートはブラウザが毎秒POSTする。**遠隔運用では**コックピットの
タブを前面に保つこと**。ブラウザはバックグラウンドのタブでタイマーを
間引く(最大約1分間隔)ため、タブを隠すと誤ってdampしうる。タブを切り替えて
作業する現場では `--heartbeat-sec` を伸ばすか、監視は twin.py 等の別画面で行う。

★**安全監視は制御ループから独立した100Hzスレッドで走る。**
50Hzループが方策の読み込みやSDKのRPCで詰まっても、監視と停止は生き続ける。

★**一度止まるとラッチする。**解除は [1. ARM] / [▶ 単体実行] を押したときのみ
(ログに残る)。ラッチ中は一切の指令を受け付けないので、詰まっていた処理が
後から古い目標を書きに来ても上書きされない。画面の「制御権」タイルが赤く
`E-STOP` と出る。

dampは実機のdampモード実測値(脚kd=5、足首kd=0.2)と同じ。
**ソフトのdampは物理E-stopの代替にはならない。**出るのは `rt/lowcmd` の
dampであって、モータ電源は切れない。**必ず併用すること。**

### 目標ガード(実機へ出る指令の最後の関所)

`set_target()` が唯一の入口。**ゲイン(kp/kd)には絶対に触らない** —
崩れかけの機体から支持力を奪うガードは事故そのものになる。

| ガード | しきい値 | 掛かったら |
|---|---|---|
| NaN/Inf | 拒否して直前の目標を保持 | 3コマ連続でDAMP |
| 可動域の外枠 | 可動域 ±0.75 rad | 正常時は絶対に掛からない(=壊れた指令) |
| 1ステップの変化量 | 1.5 rad/step | 同上 |

回数は画面下と `run<NN>_設定.json` の `guard` に残る。`guard_over`
(素の可動域からのはみ出し)だけは正常でも0にならない — 方策が
機械的ストッパへ押し付けている量で、**ガードは書き換えず数えるだけ**。

## 6. 初回投入のチェックリスト(WP8準拠)

0. `python3 real/preflight.py --iface enp46s0` が **NG 0** であること
1. `--sim` で全手順を通しで練習(UIの操作・E-STOPの位置を体に入れる)
2. 実機・**完全に吊った状態**で: ARM→START(補間)まで。関節が滑らかに
   開始姿勢へ動くこと、ログの傾き・速度が暴れないことを確認
3. 吊ったまま climb フェーズを1回実行(空中で脚が登り動作をなぞる)
4. 接地して(ハーネスは軽く張る): sitのみ("(skip)"で登り・旋回を省略し、
   段上・椅子前に手で立たせて着座単体)→ climb単体 → 通し
5. 各回のログ(`logs/real/cockpit_*/`)をsimと突き合わせ(SIM_SUMMARY.md §5)

## 7. トラブルシューティング

| 症状 | 対処 |
|---|---|
| 起動時 `LowStateが5秒来ない` | NICのUP/IP設定、LANケーブル、pingを確認 |
| `★DAMP: 指令の送信が停止` | 500Hz送信が止まった。コンソールの `lowcmd送信に失敗` を見る。DDS/NICを疑う |
| `★指令が届いていません` | 制御権が移っていない。別ターミナルの `probe_lowcmd.py` で送信元とHzを見る(2種類混在=モータの取り合い) |
| ボタンを押しても反応がない | 画面下に「●処理中」が出ていないか。SDKのRPC待ちなら最大5秒で打ち切られる |
| E-STOP後に何も動かない | ラッチ中。[1. ARM] か [▶ 単体実行] で解除される |
| `MotionSwitcherの解放に失敗` | リモコンで実機をdampにしてから再起動。`rt/lowcmd` を他プロセスが占有していないか(REAL_ROBOT.md) |
| STARTで振動・異音 | 即E-STOP。ゲイン応答の個体差の可能性 → real/calib.py で単関節応答を再測定 |
| フェーズ中に毎回同じ場所でdamp | ログをsim再生と比較(モデル誤差)。まず climb_slow_r2 等の頑健パターンに変更 |
| 旋回の終端がずれる | 開始位置マーキング精度を確認。恒常的なら AprilTag 導入(cockpitのxy_offを置換) |
| UIが更新されない | サーバのコンソールエラーを確認。ポート8090の重複に注意 |
