## 4. 今日の実行順序

### 方策に入る前のモードは `stand`(FSM 4)。walk からは入らない

**結論: `damp` → `stand` → 静止を確認 → [custom] → 方策。**

Unitree公式に「床上で純正balanceから自作方策へ無瞬断で渡す」手順は**存在しない**。
公式の低レベル例は `ReleaseMode()` のあと5秒待ってから publisher を作る
(吊り下げ/横たわり前提)。`unitree_rl_gym` は 吊り下げ→ゼロトルク→
2秒補間→policy、`unitree_rl_lab` は Passive→FixStand(3秒)→RLBase。
**どれも純正balanceから奪う形ではない。**

うちの 2026-08-24 の実測(7走行)。引き継ぎ直後(方策開始時点)の傾き:

| 直前のモード | 回数 | 方策開始時の傾き |
|---|---|---|
| `stand`(FSM 4) | 6 | 0 / 0 / 4 / 1 / 1 / 2 度 |
| `walk`(FSM 200) | 1 | **7 度**(全7走行で最大) |

n=1なので断定はしないが、機序ははっきりしている。**ウォーキングFSMは
内蔵の目標が毎tick変わる**ので、その途中で「いまの関節角」をラッチして
保持すると、**重心移動の途中の姿勢を固めてしまう**。`stand` は目標が
ほぼ静的なので、ラッチした姿勢が釣り合いに近い。

**今回から `stop_move()`(内蔵の速度指令をゼロ)を引き継ぎの前に呼び、
0.3秒待つようにした。**これまで呼んでいなかった。`stand` では無害なので
モードを問わず実行される。イベントログに引き継ぎ直前の角速度が残るので、
静定してから掴めているかを後から確認できる。

やむを得ず walk から入るときは、**歩行を止めて数秒待ち、完全に静止してから**
[custom] を押すこと。

### フェーズA: ハンドオーバー単体の検証(方策を動かさない)

**吊り下げた状態で**、次を確認する。ここが通らなければ以降は無意味。

1. 実機をリモコンで純正のバランス立位にする
2. コックピットで **[custom]** を押す(方策は開始しない)
3. **そのまま10秒放置**して観察する

| 結果 | 意味 | 次 |
|---|---|---|
| 姿勢が保たれる | 引き継ぎ成功 | フェーズBへ |
| 一瞬でも脱力する | 送信順序がまだ逆 | `real_robot.py` の `ensure_custom` を確認 |
| じわじわ崩れる | 指令が届いていない | `mode_pr` / 二重publish を疑う(§7) |

**2つ目・3つ目が出たら今日は方策を動かさない。**原因を切り分けて終わる方が価値がある。

### フェーズB: 着座の本番(椅子は真後ろ)

椅子はロボットの**真後ろ**に置く。毎回、巻尺で以下を記録:
- 座面高さ、段の面からの距離、椅子のヨー、開始位置のマーキングからのずれ

| 順 | パターン | 回数 | 目的 |
|---|---|---|---|
| 1 | `sit_up_rc_r2` | 2 | **アンカー**。前回と同じものを最初に回して、環境が前回と同じか確認 |
| 2 | `sit_up_deep_r2` | 3〜5 | **本命**。深座り版(rc比+6.7cm深い) |
| 3 | `sit_up_rc_r2` | 1 | 終わりにもう一度アンカー(温度上昇の影響を見る) |

**アンカーを最初と最後に入れるのが重要。**前回の「数値では成功」問題は、
比較対象なしで測っていたことも一因。

## 6. 今日いちばん見てほしい現象:「ずり落ち」

シムで再現できた失敗。一度きちんと座ってから、**4.6秒かけて骨盤が7.8cm沈み、
尻荷重が219N→76Nへ抜けていく**(体重が座面から脚へ戻る)。
前回の「完走したのにハーネスが体重を受けていた」はこれの可能性が高い。

**8/24のログにも同じことが起きている。**最初の走行(`sit_up_rc_r2`)は

```
09:27:21 フェーズ完走: sit_up_rc_r2
09:27:23 ★DAMP: 傾き40度        ← 完走の2秒後に倒れている
```

完走したあと2秒で40度傾いて自動DAMPしている。**完走 ≠ 安定。**

**着座後5秒は必ず観察を続ける。**着座した瞬間だけ見て成功と判断しない。

見分け方(現場で目視できる):
- 座った直後の骨盤の高さを覚えておく
- そこから**じりじり下がっていくなら、ずり落ち**
- まともに座れている場合、シムでの沈みは0〜6mm(ほぼ動かない)

**シムでの発生率は 39本中1本(3%)。**沈みの分布は二値で、38本が0〜6mm、
1本だけ67mm(中央1mm / 90%点4mm / 最大67mm)。

→ **今日5回程度なら、予測としては全部きれいに座るはず。**
もし2回3回とずり落ちるなら、**シムが実機を過小評価している**ということで、
それ自体が今日いちばん大きな発見になる。回数と沈み具合を必ずメモすること。

**ハーネスを一瞬だけ緩めて体重が座面に乗っているか確かめる**のが最も確実。
ただし必ず1人が支えられる位置に立つこと。

## 7. 絶対にやってはいけないこと

1. **解放してから送信を始めない。**必ず「現姿勢保持の送信 → 後から解放」。
   逆順は必ず脱力する。
2. **`__init__` で `ReleaseMode()` を呼ばない。**接続=観測のみ。
   立位中にアプリを起動した瞬間に脱力する。
3. **E-STOPをキューに載せない。**SDKのRPCを50Hz制御ループの中で呼ばない。
   応答が返らないとループごと止まり、安全監視まで死ぬ。
4. **同じ `rt/lowcmd` に別プロセスからpublishしない。**
   残骸プロセスが500Hzで送り続けて、実機が60分唸り続けた実績がある。
   起動前に必ず確認:
   ```bash
   ps -eo pid,comm,args | grep -E "cockpit|run_fsm|listen" | grep -v grep
   ```
5. **失敗したログを消さない。**失敗ログの方が価値が高い。
6. **静的な前傾から開始しない。**傾きが大きいのに角速度がほぼゼロの状態は
   どの方策でも回復不能(実測0/10)。コックピットが自動で弾くが、
   目視でも「大きく傾いて止まっている」なら一度立て直す。

## 8. うまくいかないときの切り分け順

貼っていただいた指摘の順序と同じ。**方策を疑うのは最後**。

1. **制御権の空白** → フェーズAで確認済みのはず
2. **LowCmd の mode / gain 初期化**
   - 全モータの `motor_cmd[i].mode == 1`
   - `mode_machine` が `lowstate.mode_machine` と一致(実測5)
   - **`mode_pr`** ← ここだけ未検証。現行コードは `0` 決め打ち。
     足首のPR(pitch/roll)とAB(並列モータ)を取り違えていないか
   - CRCが毎回更新されている
3. **初回 q / action の不連続**
4. **観測の契約**(関節順・スケール・履歴)
5. **最後に本来のsim2realダイナミクス**

### 症状別の一次容疑

| 症状 | まず疑う |
|---|---|
| 切替と同時に落ちる | 制御権の空白(§0) |
| 最初の1フレームだけ跳ぶ | default pose / action初期値 / 関節マッピング |
| 指令は連続なのに数フレーム後に倒れる | 観測の順番・履歴・位相 |
| 高周波に震える | ゲイン / action scale / 遅延 |
| 四肢が伸びる・激しく痙攣する | 関節順 / 観測順 / PR・AB取り違え |
| 何もしていないのに唸る | 残留プロセス(§7-4) |

## 9. 取るログ

コックピットが `logs/real/cockpit_YYYYMMDD_HHMMSS/` に自動保存する。
**形式は 8/24 の現場版と同じものに戻してある**(手元のリポジトリ版は
古い形式で書いており、`log_view.py` / `ab_report.py` が読めなかった)。

```
run01_設定.json            その回の設定(方策・kp/kd・関節名・開始温度・meta)
run01_0_sit_up_deep_r2.npz 毎コマの記録。100コマごとに逐次保存
イベント.log                操作と引き継ぎの時刻つき記録
```

`.npz` の中身: `rec`(T×188)+ `cols`(列名)+ `obs`(T×615)+ `final`。
列は `t / fsm / phase_i / elapsed_s / tilt_deg / q29 / dq29 / tau29 /
quat4 / gyro3 / target29 / act29 / temp29`。

**今回追加した2列**(末尾なので既存ツールに影響しない):

| 列 | なぜ要るか |
|---|---|
| `dt_ms` | ループ周期の実測。Pythonの尾側の遅れが実機で出ているかを**数値で**判断する |
| `ms_infer` | 観測構築+推論の所要時間(参考: 手元の実測は中央1.1ms / 予算20ms) |

**中断した回も必ず保存される**(`final=False` が「途中で終わった」印)。

確認は現地でもできる:

```bash
python3 real/log_view.py      # 1本ずつの詳細
python3 real/ab_report.py     # 方策ごとの集計(A/B比較)
```
